# Durable manual submission queue

> **Doc type:** Living reference — implemented, acceptance gates open. Last reviewed: 2026-11-04.

The manual slices of issues #86 and #87 compose Reporting, Submission, Workflows and the native shell. It does not complete screenshot capture, OCR release, withdrawal or recurring UEX lifecycle polling. The normative requirements remain in [01](plan/01-requirements.md), the context map in [02](plan/02-architecture.md), and the event contract in [11 §A6](plan/11-ddd-and-tdd.md).

## Release and send boundaries

The manual and onboarding test actions share the same durable queue. A click fixes the displayed Draft version, validated account and mode. The reference owner must acknowledge an actual bounded attempt for commodities, terminals, game versions, status levels, parameters and the selected terminal's priors before release proceeds. An offline attempt may leave the last successful cache available; a missing or stopped owner refuses release. The last validated remembered account can release offline without exposing credential values. A pending or failed replacement candidate cannot borrow that eligibility; a known refused or unknown account cannot release. Publishing cached data cannot acknowledge this refresh.

The complete Reporting gate checks the original observation time, age decisions, resolved context, current numeric assessments and approvals, older-row evidence, screenshot policy and any selected private attachment. A Report contains one side and at most 500 whole-SCU rows, including known zero stock; no limit check trims rows. Release fixes account, mode and request values in one SQLite transaction with the Report transition, job and outbox event.

Before dispatch, the session owner requires current read-only validation for the exact account. Starting any replacement credential candidate closes release eligibility and send authority immediately while retaining the displayed accepted identity. Revalidation preserves existing release eligibility without reopening a replacement candidate; only current successful validation restores sending. The owner reserves the sole HTTP submission slot before repeating current settings, reference freshness, acceptance, version, age, numeric, history and attachment checks. The write-ahead transaction compares the actual cache identity, Report and job versions and account policy before marking Sending. HTTP receives only that fixed prepared request. The client sends compiled version identity and preserves the original observation time.

The shared HTTP owner has two I/O threads, at most two blocking DNS threads and one in-flight submission. JSON/DTO processing uses one verified below-normal CPU worker with two pending slots; SQLite and image work remain outside Tokio polls on the session CPU owner. The production row budget is 1,000 rows per account in 30 minutes; the five-minute row cooldown and uncertain outcomes remain durable. Queue waits expose reasons without changing stored phase or granting authority.

## Results, recovery and notifications

Known HTTP results are saved before optional receipt lookup. A failed result save retries local persistence only. One durable enrichment claim permits at most one bounded lookup cycle; missing, partial or unverifiable identifiers never become positional row mappings. Dry-run success creates neither UEX report identities nor local priors. Only complete accepted LIVE production feedback creates accepted local priors; PTU remains separate. Cached-reference publication reads this committed history and requests no GET.

Job outcomes, Report transitions, accepted priors, screenshot-required evidence and outbox entries share the transaction. The app replays bounded batches of at most 32 immutable notification identities at startup. It acknowledges only after the current UI projection is accepted and, for applicable production success, the cached-reference signal is accepted. Full channels retain delivery; handler or acknowledgement failure leaves durable events available for replay. Handlers publish committed state and never release or submit another job.

On restart, unfinished unsent work returns to Draft and requires renewed review/release, except a refused production request still awaiting its receipt safety lookup: it remains held and resumes read-only checks. An interrupted Sending job becomes OutcomeUnknown and cannot replay automatically. Sending cancellation is refused. Account changes keep the existing job binding; the inline keep/review choice never retargets it. Partial and uncertain outcomes retain their safeguards.

## UEX refusal recovery

Corrected 2026-11-03 (R-SUB-2, R-SUB-6, R-SUB-9, R-SUB-11): the gateway makes one POST per call and retains typed error classes rather than remote message text. Connection refusal and verified connect timeout remain distinct from request timeout, reset, malformed responses and HTTP 5xx without a usable UEX status. The real 90-second timeout and an HTTP 504 each received exactly one local-mock request and became OutcomeUnknown. Known UEX codes take their documented class regardless of HTTP status. Unknown bounded technical identifiers stay visible; credential echoes and malformed identifiers do not enter persistence or diagnostics.

`SubmissionRetrySettings` defaults to three total automatic attempts, exponential delays of 5 then 10 seconds, a 60-second backoff cap and a 90-second send timeout. Only proven unprocessed requests use this backoff. Every retry re-enters the original account/mode binding and all fresh send-time checks; exhausted retries remain held for explicit Retry now or cancellation. Acceptance refusals re-enter the gate after 15 minutes; first-row duplicates wait five minutes, including after explicit retry. A duplicate within the ten-minute evidence window of a shared-key unknown attempt returns the current Report with PossiblyAlreadyReceived and a typed link to that earlier job. It never resolves or replays the earlier outcome.

Token refusals pause the whole queue, upgrade_required requires an app update, and key errors first re-check GET /user without an app token. A confirmed current account leaves the queue paused with Retry now; refused or unavailable checks retain their distinct recommended action. An HTML HTTP 404 holds the whole queue as API changed until explicit retry or an update. Report-fixable screenshot, observation-time, row-limit and terminal refusals return to Draft. Permanent technical refusals become Rejected, with the original code and compiled-version diagnostics; invalid_game_version is final and offers no same-version duplicate.

For production, per-row failures above the first row and database_error retain partial-acceptance metadata and never authorise replay. Codes not verified as before-storage first perform one bounded, account/terminal/type-filtered data_info read, matched to the attempted date_added and commodity identity. A matching row is partial acceptance. Absence is conclusive only for a complete window shorter than 100 records with valid identities; a full or malformed window, failed GET or unreadable reply stays held. A held safety check cannot be cancelled, retried as a POST or bypassed by an older shared-row release. It survives restart and repeats only read-only checks every 15 minutes. A later result is persisted with its original code and check provenance without adding a submission attempt; failed local persistence retries the save only.

Schema 10 is the forward format gate for these phases, bounded codes and receipt-check metadata. Existing schema-nine documents retain their exact values and attempts; absent receipt-check metadata means no such check occurred. Migration requires the coordinated exact database/settings backup, and schema-nine binaries refuse the newer database. Configuration stays at schema 6. Public local-HTTP, real SQLite, injected-clock and drawn keyboard contracts verify this slice. Detailed partial/unknown row resolution, split/correction actions, daily-quota reset scheduling, real-service/native/provider acceptance and a valid full mutation campaign remain with their owning gates. Daily-quota exhaustion currently stops sending safely rather than inventing its reset time.

Global account, API-change and daily-quota causes are stored transactionally in a typed service fence independent of Report state. Cancelling or returning the originating Report cannot clear the fence. Explicit Retry now acknowledges a recoverable account/API cause without replaying a cancelled Report; a version lockout cannot be acknowledged in the same build. Daily quota has no implicit reset from time, credentials, cancellation or Retry now; token-scoped reset and resumption remain the separate quota feature. The global cause stays visible even without an active Report row. Schema 10 also stores the fence and explicit acknowledgement; older documents default to no acknowledgement.

A version lockout retains the originating compiled stable release in its attempt outcome. Explicit Retry now becomes available only when the queue owner's validated compiled Release identity has a strictly greater canonical numeric release version. The existing release policy accepts only vMAJOR.MINOR.PATCH; prerelease/build suffixes, development, unknown origins, the same release and downgrades provide no recovery authority. Source/signature authentication remains the release pipeline's responsibility. Startup never clears this fence or creates a POST. A cancelled or restart-returned Report is acknowledged without replay; its Draft still needs normal release. A queued retry records its newer-release decision in exact attempt history. The canonical release value is shared by update and submission policy and re-exported through the existing workflows API.

## Recovery scope and compatibility evidence

Corrected 2026-11-03: AccountRefusal carries the original HTTP status, an optional safe bounded code and the account action independently of the existing receipt result. An unavailable receipt window remains Held, matching receipt evidence remains partial, and an unsafe echoed identifier is absent from history. HTTP 401/403 with an unsafe identifier retains a typed account refusal; production receipt certainty stays unknown. Each answer and its global AccountPause fence commit together before any account/receipt GET or another Report can dispatch. Key refusals retain a separate Pending account check; the existing owned recovery performs GET /user only after that commit. Completed account-check evidence stores its closed action without setting receipt_checked or reopening sending. A pending account check offers neither Retry now nor queue acknowledgement. Explicit queue acknowledgement leaves the originating held, partial or unknown request permanently closed to POST replay, including after a later receipt result. A known-unprocessed paused Report can return to review by cancellation and still requires normal renewed release. The exact original HTTP status, safe optional code, original action and originating committed revision remain in the immutable attempt after an allowed retry. A later receipt result retains that provenance. Its pending GET may follow one acknowledgement revision only when the complete immutable request, attempts, result and phase still match; another attempt or request receives no authority from that GET.

Safe unlisted identifiers are nonempty ASCII letters, digits, underscore or hyphen, bounded to 128 bytes. Their case and spelling are retained. Control characters, other punctuation, non-ASCII text, excessive length and credential echoes remain excluded. This grammar describes client handling, not newly observed UEX codes.

The schema-nine migration fixture is synthetic and source-bound to parent `67fed6d45b4b777790e5e362b61f0a9a873eb60d`. Its SQL uses that parent's schema-one, two, three, six and nine DDL; the intermediate payload-only migrations operate before any synthetic Reports are inserted. Literal Report/job/attempt/outbox documents use the parent's `reports.rs`, `report_lifecycle.rs` and `queue_document.rs` formats. Tests exercise an actual SQLite file, backup refusal, migration rollback, exact stored payload preservation and reopening through the public storage ports. No current database is downgraded to produce this fixture, and no execution of an older binary is claimed. The exact historical read-only admission guard is also compiled as a test fixture: it admits the version-nine file and refuses the migrated version-ten file. This checks that source-bound guard, without executing an older application binary or decoder.

## Repeated account-check persistence correction (2026-11-04)

Corrected 2026-11-04 (R-SUB-2, R-SUB-9, R-SUB-11): each attempt retains the ordered account-check actions that changed its state. An unavailable check followed by a successful or refused check reconstructs both validated transitions, including when receipt settlement, cancellation, restart return or queue-only acknowledgement intervenes. Repeated identical unavailable results remain idempotent. Reconstruction rejects missing, redundant or invalid actions and still requires exact revision, attempt, phase and result equality; the storage encoder validates that round trip before saving. Legacy single-check documents infer only the one action actually recorded, without inventing missing transitions. This refines the unreleased schema-ten recovery format; schema-nine backup/migration and settings schema six remain unchanged.

The UEX adapter translates permanent refusals into a closed correction disposition independently of the opaque safe code retained for display. A rejected captured game version requires a new capture; other permanent refusals retain the client update/report recommendation. Storage writes the typed disposition and translates legacy code-only refusal documents at its adapter boundary. No duplicate-as-new-Draft command is added. Release and dispatch ordering consume the same domain query for unresolved receipt evidence.
